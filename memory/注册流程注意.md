# BLS 中国站注册流程

## Step 1: 获取注册页面 (RegisterUser)

**请求**:
```
GET /CHN/account/RegisterUser
```

**响应**: HTML 页面，包含隐藏字段

**关键隐藏字段**:
| 字段名 | 来源 | 用途 |
|--------|------|------|
| `SecurityCode` | 页面隐藏字段 | 用于某些请求的 data 参数 |
| `CaptchaId` | 页面隐藏字段 | **用于 SendRegisterUserVerificationCode 请求** |
| `__RequestVerificationToken` | 页面隐藏字段 | 防伪令牌 |

**重要**: 页面 HTML 中还有 `win.iframeOpenUrl` 变量，**这是 Step2 验证码页面的 URL**！

---

## Step 2: 获取验证码 (GenerateCaptcha)

**请求**:
```
GET /CHN/CaptchaPublic/GenerateCaptcha?data={SecurityCode}
```

**重要**: Step2 的 URL 来自 `win.iframeOpenUrl`（**不是 SecurityCode 隐藏字段！**）

**具体来源**:
```javascript
// 在 Step1 响应 HTML 中找到：
win.iframeOpenUrl = '/CHN/CaptchaPublic/GenerateCaptcha?data=xxx';
```

**验证方法**: 在 HAR 包中找 Step2 请求的完整 URL，在 Step1 响应 body 中搜索相同值。

**响应**: HTML 页面，包含 9 张图片（3x3 grid 排列）

**验证码结构**:
- CSS 中有大量混淆的 class，每个图片对应一个 div
- 图片 div 有 position:absolute，left/top 决定位置
- 9 个格子位置: (0,0), (0,110), (0,220), (110,0), (110,110), (110,220), (220,0), (220,110), (220,220)
- 每个位置可能有多层图片（不同 z-index），取最高 z-index 的可见图片
- 部分图片可能被 CSS `display:none` 或 jQuery `hide()` 隐藏

---

## Step 3: 提交验证码 (SubmitCaptcha)

**请求**:
```
POST /CHN/CaptchaPublic/SubmitCaptcha
Content-Type: application/x-www-form-urlencoded

SelectedImages={选中的图片ID列表,分隔}&Id={SecurityCode}&Captcha={SignData}&__RequestVerificationToken={token}
```

**Body 参数**:
| 参数 | 来源 | 说明 |
|------|------|------|
| `SelectedImages` | 用户选择 | 逗号分隔的图片 ID |
| `Id` | Step1 的 SecurityCode | 保持不变 |
| `Captcha` | 来自 GenerateCaptcha 页面的隐藏字段 | 防伪签名 |
| `__RequestVerificationToken` | GenerateCaptcha 页面 | 防伪令牌 |

**响应**:
```json
{
  "success": true,
  "captcha": "xxx",     // 用于后续请求的 captchaData
  "captchaId": "xxx"    // ⚠️ 这是 SubmitCaptcha 自己的 ID，不是 RegisterUser 的 CaptchaId！
}
```

**注意**: SubmitCaptcha 返回的 `captchaId` **不是**后续 SendRegisterUserVerificationCode 使用的 captchaId！

---

## Step 4: 发送注册验证码 (SendRegisterUserVerificationCode)

**请求**:
```
POST /CHN/account/SendRegisterUserVerificationCode?email=xxx&mobile=xxx&isMobileVerify=False&data=xxx&captchaData=xxx&captchaId=xxx
```

**Query 参数**:
| 参数 | 来源 | 说明 |
|------|------|------|
| `email` | 用户输入 | 邮箱地址（**@ 不能被编码成 %40**） |
| `mobile` | 用户输入 | 手机号 |
| `isMobileVerify` | 固定 | "False" |
| `data` | Step1 SecurityCode | 需要保持原始编码 |
| `captchaData` | Step3 响应的 `captcha` | 验证码数据 |
| `captchaId` | **Step1 的 CaptchaId** | ⚠️ 不是 Step3 返回的 captchaId！ |

**重要**: email 参数中的 `@` 符号**不能被 URL 编码成 `%40`**！
- 使用 `urlencode(query_params, safe="@:")` 保留 `@` 和 `:`

---

## 参数来源汇总

| 参数 | Step1 来源 | Step2 来源 | Step3 来源 | Step4 来源 |
|------|-----------|-----------|-----------|-----------|
| SecurityCode | 隐藏字段 SecurityCode | - | - | - |
| **iframeOpenUrl** | **JavaScript 变量 win.iframeOpenUrl** | **Step2 URL 来源** | - | - |
| CaptchaId | **隐藏字段 CaptchaId** | - | - | **Query captchaId 参数** |
| captchaData | - | - | 响应 captcha 字段 | Query captchaData 参数 |
| __RequestVerificationToken | 隐藏字段 | - | Body 参数 | Header |

---

## 验证码解析要点

### HTML 结构特点
- 图片 div 有混淆的 class 名
- position:absolute 控制位置
- 9 个格子: (0,0) 到 (220,220)，步长 110px

### 解析步骤
1. 提取 CSS 中的 left/top/z-index 规则
2. 提取 jQuery show()/hide() 调用
3. 解析 img 标签的父 div
4. 每个格子位置取最高 z-index 的可见 div
5. OCR 识别数字，选择匹配的图片

### OCR 识别要点

⚠️ **重要结论**: OCR 识别率超级高，ddddocr 识别不可能是问题关键！

- ddddocr 识别率极高，正常情况下不需要担心识别错误
- 如果验证码验证失败，问题几乎肯定在**图片可见性判断**或**参数传递**，而不是 OCR
- 不要在 OCR 识别上浪费时间排查

### 已知问题
- HTML 可能缺少 `</div>` 闭合标签（BeautifulSoup 解析不完整）
- 部分图片被 CSS display:none 或 jQuery hide() 隐藏
- 需要备用正则解析方案

---

## ⚠️ 常见错误

1. **captchaId 用错来源**:
   - ❌ 错误: 使用 SubmitCaptcha 响应的 captchaId
   - ✅ 正确: 使用 RegisterUser 页面的 CaptchaId 隐藏字段

2. **Step2 URL 错误**:
   - ❌ 错误: 使用 SecurityCode 构造 `/CHN/CaptchaPublic/GenerateCaptcha?data=xxx`
   - ✅ 正确: 使用 `win.iframeOpenUrl` 的完整 URL

3. **email 参数被 URL 编码**:
   - ❌ 错误: `requests` 自动把 `@` 编码成 `%40`
   - ✅ 正确: 使用 `urlencode(params, safe="@:")` 直接拼接到 URL

4. **图片解析遗漏**:
   - HTML 可能缺少 `</div>` 闭合标签
   - 需要使用正则备用解析
   - 需要过滤 jQuery `hide()` 隐藏的图片

# 🔴 重要经验教训（2026-05-27）

## ⚠️ HAR 包逆向分析核心原则

**问题根因**：没有严格从 HAR 包中逆向推导每个请求参数的来源，导致用错误的参数浪费了大量时间。

### 核心原则

1. **逆向追溯参数来源**
   - 当分析第 N 步请求时，必须从第 N-1、N-2、N-3... 步的响应 body 中找数据
   - **绝对不能想当然地猜测参数来自哪里**
   - **数据必须完全一致，不能有任何不同**

2. **具体操作步骤**
   ```
   假设要分析 Step16 的请求参数：
   ↓
   从 HAR 包中找到 Step16 的请求
   ↓
   提取 Step16 请求的所有 query/body 参数
   ↓
   逐一追溯每个参数：
     - 参数 A 来自哪里？
     - 在 Step15/14/13/12... 的响应 body 中搜索相同值
     - 找到来源后，用正则精确匹配，确认格式完全一致
   ↓
   用找到的来源数据构造 Step16 请求
   ```

3. **常见错误**
   ```
   ❌ 错误做法：
   "security_code 应该来自上一步的 hidden 字段"
   "captchaId 应该是上一步返回的 id"
   "data 参数应该是 URL 解码后的值"
   
   ✅ 正确做法：
   "从 HAR 包中找到 Step15 的响应 body
    用正则提取 data 参数的精确值
    在 Step16 中使用完全相同的值"
   ```

### 具体案例

**问题**：Step2 验证码页面的 URL 来自哪里？

**错误分析**：
```
❌ 认为：Step2 URL = /CHN/CaptchaPublic/GenerateCaptcha?data={Step1的SecurityCode}
原因：SecurityCode 是 data 参数，猜测它用于构造验证码页面 URL
```

**正确分析**：
```
✅ 在 HAR 包中搜索 Step2 请求的完整 URL
   ↓
   找到类似：/CHN/CaptchaPublic/GenerateCaptcha?data=xxx
   ↓
   提取 data 参数的精确值
   ↓
   在 Step1 的响应 body 中搜索这个值
   ↓
   找到：win.iframeOpenUrl = '完整URL'
   ↓
   结论：Step2 URL 来自 win.iframeOpenUrl，不是 SecurityCode
```

### 调试建议

1. **打印请求的完整 URL 和参数**
   ```python
   # 在发送请求前打印
   print(f"请求 URL: {url}")
   print(f"请求参数: {params}")
   # 与 HAR 包中的请求完全对比
   ```

2. **逐字节比对关键参数**
   ```python
   # 从 HAR 包复制的值
   har_value = "abc123%40test.com"
   # 代码生成的值
   code_value = generate_value()
   # 必须完全一致
   assert har_value == code_value, f"参数不匹配: HAR={har_value}, CODE={code_value}"
   ```

3. **不要假设**
   - 不要假设 "这个参数应该来自上一步"
   - 不要假设 "这个值应该是解码后的"
   - **从 HAR 包中实际找到来源**

## 📋 HAR 包分析检查清单

每次分析新请求时，必须完成以下步骤：

- [ ] 找到该请求在 HAR 包中的完整 URL（query string 完整保留）
- [ ] 找到该请求的所有 header（特别是自定义 header）
- [ ] 找到该请求的 body 内容（如果是 POST）
- [ ] **逆向追溯**每个参数的来源：
  - [ ] 参数 A：在上一步响应 body 中搜索相同值
  - [ ] 参数 B：在上上步响应 body 中搜索相同值
  - [ ] ...
- [ ] 确认数据格式完全一致（URL 编码、大小写等）
- [ ] 在代码中实现参数构造逻辑
- [ ] **再次比对**代码生成的请求与 HAR 中的请求
